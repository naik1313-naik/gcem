### 2.2 Recurrence Key Definition

**Primary recurrence key:** `(turbine_id, alarm_code)`  
**Rationale:** Same alarm code on same turbine indicates recurrence of the same fault mode.  
**Cross-turbine aggregation:** Available on request via `alarm_code` only.

### 2.3 Sensor Mapping Strategy

**Current limitation:** No sensor ID/type/location data exists.

**Proposed mapping table (to be populated when metadata available):**

```sql
CREATE TABLE sensor_catalog (
  sensor_id TEXT PRIMARY KEY,
  turbine_id TEXT REFERENCES turbines(id),
  sensor_type TEXT, -- 'vibration', 'temperature', 'pressure', 'power'
  location TEXT, -- 'gearbox_drive_end', 'gearbox_non_drive_end', 'main_bearing', etc.
  unit TEXT,
  installation_date DATE,
  manufacturer TEXT,
  model TEXT
);
```

**Until populated:** All sensor fields return `"Unknown — not available in dataset"`

## 3. Recurrence Calculation Specification

### 3.1 Required Metrics

For each `(turbine_id, alarm_code)` group:

| Metric | Definition |
|--------|------------|
| `total_occurrences` | COUNT(*) |
| `first_occurrence` | MIN(event_timestamp) |
| `last_occurrence` | MAX(event_timestamp) |
| `occurrences_24h` | COUNT where event_timestamp > NOW - 24h |
| `occurrences_7d` | COUNT where event_timestamp > NOW - 7d |
| `occurrences_30d` | COUNT where event_timestamp > NOW - 30d |
| `mean_interval_hours` | AVG(LAG(event_timestamp) diff) |
| `median_interval_hours` | MEDIAN(LAG(event_timestamp) diff) |
| `burst_detected` | TRUE if ≥3 events within 48h window |

### 3.2 Deduplication Rules

- **Do NOT deduplicate** on alarm_code alone — different turbines are separate
- **Do NOT deduplicate** on timestamp proximity — rapid re-alarms are legitimate events
- **Only deduplicate** if exact `(alarm_id, turbine_id, alarm_code, timestamp)` duplicate exists
- **Event grouping:** Each row = one alarm event occurrence

### 3.3 Timezone Handling

- All timestamps stored as UTC (timestamptz)
- Query parameters accept ISO 8601 with timezone
- Default display timezone: UTC
- User timezone override: via UI preference

## 4. ML Approach Assessment

### 4.1 Data Sufficiency Evaluation

| Criterion | Status | Notes |
|-----------|--------|-------|
| Labeled anomalies | ❌ None | No ground-truth "anomalous recurrence" labels |
| Temporal depth | ❌ 6 days | Need ≥90 days for seasonal baseline |
| Sample size | ❌ 16 events | Need 100s for ML |
| Turbine diversity | ⚠️ 10 turbines | But only 1-4 events each |
| Feature richness | ⚠️ 4 sensors | Only at alarm time, not continuous |

**Conclusion:** **ML model NOT justified** for current dataset. Deterministic statistical baselines are more appropriate.

### 4.2 Recommended Statistical Baseline

1. **Rolling window rates:** Events per turbine per alarm_code per 7-day window
2. **Threshold alerts:** Flag when 7-day rate > 2× historical median rate
3. **Burst detection:** ≥3 events in 48h window
4. **Cross-turbine comparison:** Rank turbines by recurrence rate per alarm_code

### 4.3 Future ML Triggers

Train ML model when:
- ≥90 days of data across ≥5 turbines
- ≥50 alarm events per major alarm_code
- Ground-truth labels available (maintenance-confirmed anomalies)
